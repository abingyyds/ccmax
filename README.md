# CCMAX

CCMAX 帮助 Claude Max 账号持有人按有效用量获取收入，并为代理提供邀请注册、独立报价、账单和提现管理。当前后台适配：

- 平台 A：平台主账号 OAuth 上号、实时账号同步。
- 平台 B：平台主账号 OAuth 上号、refresh token 导入、账号同步和历史用量查询。
- 平台 C：Cookie 会话登录、OAuth 上号、refresh token 导入、账号同步、启停和历史用量查询；新账号按上游规则固定使用默认策略、分组和 CC 模板。
- 平台 D：Bearer 会话登录、OAuth 上号、refresh token 导入、账号同步、启停、代理同步、模型用量和历史用量查询。

对代理统一显示 **平台 A、平台 B、平台 C、平台 D**。浏览器公共资源、代理 API、平台筛选、报价、邀请、任务错误和 CSV 导出均不提供真实来源名称或网址；真实平台资料只在管理员专属接口和配置界面显示。已有数据库平台键、账号绑定、历史折扣和资金记录不变，无需迁移或重新报价。API 对接使用字母标识，见 [代理 API](docs/AGENT_API.md)。

代理只登录 CCMAX。Claude 账号提交到平台主账号，账号经真实授权邮箱校验或管理员核实后，在 CCMAX 中固定归属于对应用户；同一个 Claude 账号可以绑定多个平台。平台密码、refresh token 和 OAuth 会话只在服务器端加密处理，浏览器不会得到主账号密码。

**每个 Claude 账号必须绑定一条固定出口代理，同一账号上到所有平台时统一使用这条代理，一条代理只能被一个账号占用。** 支持 HTTP、HTTPS 和 SOCKS5H；SOCKS5 地址统一转成 SOCKS5H。未绑定或已禁止上号时，系统阻止新授权、RT 导入和启用操作。代理只在账号层绑定一次，支持的平台由后台自动同步，其他平台的同步状态不会阻塞新平台授权。

## Railway 部署

1. 在 Railway 新建一个 Project，添加 **PostgreSQL** 服务。
2. 选择「Deploy from GitHub Repo」，选择 `abingyyds/ccmax`；Railway 会读取根目录 `Dockerfile` 构建。
3. 在 CCMAX 服务的 Variables 中设置以下变量（`DATABASE_URL` 使用 Railway 的变量引用）：

   ```text
   DATABASE_URL=${{Postgres.DATABASE_URL}}
   ENCRYPTION_KEY=<64 位十六进制，生成：openssl rand -hex 32>
   ADMIN_EMAIL=<首次平台管理员邮箱>
   ADMIN_PASSWORD=<至少 12 位的首次密码>
   ADMIN_NAME=平台管理员
   APP_URL=https://你的域名
   SYNC_INTERVAL_SECONDS=300
   ```

   `ENCRYPTION_KEY` 必须长期保留；更换它会使已保存的平台密码和上游令牌无法解密。生产环境没有默认账号、默认密码；新用户通过上级创建的邀请链接注册，或由上级手动开通。
4. 在 Settings → Networking → Generate Domain 生成域名，把生成的 HTTPS 地址填入 `APP_URL` 后重新部署。仅使用 Railway 默认域名时，也可不填 `APP_URL`，系统自动使用 `RAILWAY_PUBLIC_DOMAIN` 的 HTTPS 地址；自定义域名应明确填写 `APP_URL`。首次自动构建如因变量未设置而失败，补齐变量后 Redeploy 即可。
5. Healthcheck 使用 `/health`；首次启动会自动执行数据库迁移并创建唯一的平台管理员。后续部署不会覆盖用户、平台连接、账单或流水。
6. 首次登录后在「平台管理」录入上游主账号，在「代理团队」创建下级并设置价格；同步已有账号后分配归属。在「出口代理」添加实际代理，再到账号的「代理」入口绑定；旧账号绑定后由后台统一处理平台代理，平台 A 如需恢复会提示重新授权并自动沿用账号代理。

PostgreSQL 服务若被重命名，`DATABASE_URL` 引用中的 `Postgres` 也要改为实际服务名。应用服务无需挂载本地磁盘；数据库持久化由 PostgreSQL 服务管理。初期保持一个应用副本，使用 Dockerfile 的默认启动命令，Railway 自动注入 PORT。

生产环境不要设置 `ALLOW_LOCAL_DB=true`，也不要把 `.env`、平台密码或 refresh token 提交到 GitHub。Railway PostgreSQL 建议开启自动备份，并在正式运营前做一次恢复演练。

已有 Railway 部署：在应用服务的 Settings → Source 选择本仓库的 `main` 分支，拉取最新提交重新部署；启用自动部署时，push 后会触发构建。保留原 `DATABASE_URL` 和 `ENCRYPTION_KEY`。首次启动自动执行所有缺少的迁移（当前至第 15 版 平台 D 平台）；已有用户、账单、报价和流水保留。部署完成后检查 `/health`，后台自动启动采集，无需手动点击。

## 使用顺序

1. 平台管理员在「平台管理」选择平台、填写自己的主账号和该连接的上游结算折扣；系统先登录核验，再同步平台账号。平台 C 的上游地址由服务端私有适配器配置，凭据在 CCMAX 数据库中加密保存，服务器到此上游的连接使用 HTTP；如上游提供 HTTPS，应更新适配器地址。
2. 在「账号管理」新建 Claude 账号，先选择自己添加的未占用代理，也可直接「添加并绑定代理」，然后选择平台上号。多平台 OAuth 可批量生成独立授权链接，选择四个平台就必须分别完成四次授权，不能共享同一回调或 code；平台 B、平台 C 和 平台 D 也可以导入 refresh token。四个平台的 OAuth 都需粘贴完整回调地址或 `code#state`，服务器在入队前核验当前流程的 state，并用授权码摘要拦截跨平台重复兑换。校验失败保留原授权流程，不提交上游。
3. 管理员把同步出的未归属账号分配给团队成员。归属确认后不能自行更换，避免账单漂移。确认时会为所有未封账日期补全收益链；应先配置各层真实合同的历史起始价格，缺价会回滚分配。
4. 在「代理团队」创建直属下级并为每个平台设置 0–1 折扣。初始价格可填写真实合同起始日以支持历史导入；后续新价格从次日北京时间生效，平台给 CCMAX 的上游折扣也按生效日留档，历史日账单不会套用后来改过的价格。
   **已有代理接入新平台时，每一层直属上级都需先为下级设置该平台价格**。首次报价可从真实合同起始日生效；新平台不会复制 平台 B 的折扣，也不会默认为零。创建成员及编辑其他报价时可留空保持未定价；邀请链接默认仅勾选本人已定价的平台。归属账号的代理链缺少当日价格时，平台账号、遥测和原始用量仍会保存并标记为待计费，不会生成收益或账单；补齐价格后重新同步即可完成归因。
5. 「用量明细」中的今日实时数据只用于预估。每天北京时间 02:00 后，系统自动拉取已结束日期的上游完整日账单、保存原始金额、校验归属和当日价格，并自动封账、生成各层代理的待确认结算账单。历史接口返回 403/404 时可使用明确标记的日终快照预估；平台 A 默认启用此方式。不为缺席账号补零。
6. 自动账单生成后，按「平台 → 直属代理 → 更下级」逐级确认真实回款及结算。管理员核实日终快照时可同时填写上游回款凭证，让本层利润进入可提现余额；确认会把本层利润写入不可重复的流水账。提现先冻结余额，再由直属上级线下打款并登记凭证。

## 邀请注册与不同报价

在「代理团队 → 邀请链接 → 创建邀请链接」为不同客户生成不同报价的链接。每条链接可分别选择平台并设置 0–1、最多四位小数的结算折扣，支持 0 折扣。可设置有效期（默认 30 天，也可长期有效）和注册人数上限；人数留空不限，填写 1 即为单人邀请。每位代理最多保留 100 条有效链接。

每条有效邀请可「复制链接」或「复制推广文案」；创建人还可以编辑链接折扣。推广文案包含专属邀请地址、实际应收查看方式与结算条件，不预填收益承诺。

对方打开链接后可以先查看自己的各平台结算折扣，再自行填写名称、邮箱和至少 12 位密码。注册成功后自动成为链接创建人的直属下级，按北京时间注册当日保存初始价格；未选平台保持未定价。注册后使用自己的邮箱和密码登录，无需上级代设、传递密码。已有邮箱不能通过邀请重新挂靠或覆盖价格。

链接报价可由创建人编辑；旧链接编辑时也可以补充后来新增且已定价的平台。修改只影响之后通过该链接注册的新成员；已注册成员的归属和价格保持不变。链接仅由创建人查看、复制、编辑和停用；任何持有有效链接的人均可按当前报价注册，请仅分享给目标客户。到期、停用、人数已满，或邀请人及其任何上级停用时，链接不可继续注册。注册名额与账号、价格和审计记录在同一事务提交，并发注册不会超额占用名额。

停用链接不修改已注册成员的归属和价格。已注册成员仍通过现有「定价」或「批量调价」管理后续报价，已有价格变更从次日北京时间生效。数据库第 14 版自动新增邀请、邀请报价和注册记录，保留已有用户和财务数据，无需新增环境变量。

## Max 20x 额度与实际收益

官方 Max 20x 为 $200/月，每 5 小时额度为 Pro 的 20 倍，另有独立周限制；官方未公布统一的周/月 Token 数或美元用量。另含的 $200/月 API credits 有独立领取条件及用途，不是 Claude Code 订阅额度或现金收入。详见 [官方规则核查](docs/MAX20X_USAGE.md)。

登录页与邀请注册页统一以「让闲置 Max 额度，变成看得见的收益」介绍服务，手机端先展示报价与注册表单，再介绍收益流程和常见问题。邀请注册页以账号变现为主线，展示链接实际报价，注册后直接登录并添加账号。核算输入不预填假设额度或成本。总览按本人已核实归属的账号展示近 7 / 30 个已结束日期的实际应收和已确认利润；采用每日冻结价格，显示账号渠道日覆盖，排除快照、实时预估及下级账号。完整 30 天账单及实际成本齐全后才计算扣成本收入。近 30 天是固定统计窗口，不冒充官方自然月额度。

## 每日自动账单与日终快照

系统默认启用每日采集，不需要新增环境变量。北京时间 02:00 后开始查询昨日完整日账单；失败按 5–60 分钟退避重试，归属/价格等业务异常每小时重试。启动和日常巡检会补齐最近 30 天内从平台接入、最早已存用量或合同起始日起的缺失日期。最近 3 天的成功账单每 6 小时复查；更早已失败日期仍继续重试。首次采集优先处理较近日期，按平台限制活动任务数量。

日账单任务每 10 秒更新心跳；进程中断且超过 90 秒没有心跳时，下一轮巡检会解除任务占用并允许重新排队，不再等待通用任务的 30 分钟中断检查及排队时的一小时退避。仍有心跳的长任务继续执行；真实上游请求失败仍按原退避重试。旧 worker 留下的孤立排队或执行中记录会自动恢复。Key 工作空间同步独立启动，New API / KeyMan 的请求超时覆盖响应正文读取，避免慢响应阻断每日账单调度。

平台 B / 平台 D 读取完整历史查询的全部分页；平台 C 等待 `complete=true` 且没有 pending/refreshing 后读取逐账号金额。平台 A 现在实际请求历史接口，不再按账号角色直接拒绝；2026-10-19 使用当前真实连接登录验证，`/api/admin/usage-settlements` 返回 HTTP 403，而账号、团队用量和团队结算账单列表可读，团队结算账单为空。团队总额不能替代逐 Claude 账号日账单。

平时每次账号同步都保存用量快照，独立快照 worker 全天每 5 分钟采集；北京时间 **23:55 至次日 00:10 每分钟**采集。快照保存独立于价格和收益入账，避免某个账号缺价导致其他快照回滚。三个独立快照任务并发、每页 100 个账号、每批最多 4 个账号保存；失败账号下一轮重试。任务心跳每 10 秒更新，中断超过 90 秒可恢复。23:55 是集中采集起点，不冻结金额。

每次每日任务优先直接读取平台完整日账单。历史接口实际返回 403/404 时，按连接授权使用当日最后有效快照兜底，明确标记「快照预估」；不会用快照掩盖历史金额、日期或分页校验错误。保留更早的同日末次观测，不因其距离零点超过 10 分钟就丢弃，也不取全天最大值。来源属于昨日的延迟数据可用于昨日，今日清零值不能记给昨日。计数回退保留异常，缺失不补零。

旧版 `usage_days` 已保存的同日实时用量可自动恢复至快照库，无需人工导入。优先保留原始来源时间；旧记录没有上游时间时，只允许使用实际采集日期与账单日期一致的记录，保留真实观测时间和 `usage_archive` 来源，不虚构上游时间。部署前完全没有保存的金额仍不能从未来观测推算。

「用量明细 → 账单更新记录」展示已生成的来源账单、金额及入账进度，支持只读下载。快照兜底成功时不把上游权限拒绝显示为账单失败，技术诊断单独保存。没有任何可用观测的日期显示「当日用量数据待补齐」，金额为 `—`；不会生成伪造的零元账单。原始账单先独立留档，缺归属或缺价不丢失金额；归属和历史价格补齐后自动结算，重试不重复开票。管理员和代理无需点击采集、导入或生成按钮。

每日 02:00 前，账单结算页会显示昨日账单的计划更新时间，例如 10 月 28 日凌晨显示 10 月 27 日账单将在当日 02:00 后更新。管理员可直接在结算页查看自动更新记录及异常明细；来源账单已存档但账号尚未全部入账时，保留实际排队、执行或待核对状态，只有完成处理才显示「账单已生成」。

原始日账单、快照、已封账金额和已有账本保留。上游后来修订金额与已封账不一致时保存新来源并提示冲突，不覆盖旧账或自动冲正。账单仍使用当日已存合同价格，不复制其他代理的报价。自动出账不自动确认回款、不自动转账；团队 gross 准备金只表示当前可覆盖的付款义务，实际支付仍需在线下完成并登记凭证。确认及提现继续遵守逐级资金来源校验。

数据库第 12 版新增账单库及自动出账标记，第 13 版增加快照恢复来源、独立诊断和待补齐状态；无需清库。`GET /api/billing/days`、`POST /api/billing/collect`、`GET /api/billing/statements/:id` 仅管理员网页会话可用，原始异常及上游明细不向下级暴露。下级仍能在原有用量和结算接口查看自己的金额及预估标记。

## 平台管理与结算价格

「平台管理」每张卡片都可点击「上号到此平台」，选择已有 Claude 账号或新建账号后，流程只向所选平台提交；账号固定代理规则同样适用。多平台同时上号仍从「账号管理」进入。

「账号管理 → 平台管理」按平台名称展示独立卡片和当前登录人的结算折扣，不显示主账号邮箱；待生效报价另行标明。可单独启用、停用或编辑目标状态，后台读取上游确认后才更新本地状态；失败原因及任务编号会留在卡片内。已有平台可点击「重新授权」，未接入的平台可点击「上号到此平台」。重新授权仅限已核实的账号本人或管理员，授权流程及链接只返回给发起人，强制使用固定代理、分别完成各平台 OAuth，并核对原平台 ID 和真实邮箱；保留原归属、对账绑定、用量和账单。请始终授权卡片上的原 Claude 邮箱。平台 A 主账号有上游管理员权限时，普通启停按钮同步修改上游状态；权限不足时，同一按钮自动改为只暂停或恢复 CCMAX 内使用，不伪造上游状态。

管理员看到自己的上游结算折扣；每位下级只看到直属上级给自己的当前折扣及生效日期，已有改价另列待生效折扣和北京时间日期。未定价明确显示「未定价」，不套用管理员或其他成员的价格；0 折扣按 0 显示。代理团队的定价弹窗和列表也显示当前与待生效价格，保存只提交实际变更的平台。修改下级报价不会修改管理员的上游合同价，已封账金额保持固定。

上游降价时保留已经约定的下级价格，不自动改价，也不阻止上级登记新的合同价。总览、平台管理和代理团队会提醒当前及待生效倒挂或缺价；团队页列出自己的当前/次日应收折扣、风险生效日和每 $100 平台账单的单层损失。管理员同平台多个启用主账号按最低当日应收折扣评估，任一缺价明确提示；这是报价风险评估，各笔实际账单仍使用对应连接的冻结合同价。

在「代理团队 → 批量调价」选择平台和最多 500 位**直属下级**，可使用「统一设置折扣」「按比例下调现有折扣」或「仅下调超出应收上限的报价」。比例调整基于次日待生效价，结果向下截到四位小数；上限模式只降低高于自己次日应收价的部分，该部分调至零差价。先预览当前价、原次日价、新价和差价；预览也显示受影响代理对其直属下级的倒挂/缺价，有风险必须明确确认。控制项或报价变动需重新预览，所有变价和审计在同一事务内保存。已有次日报价会被替换，未变价成员不写入。

批量新价格统一在**次日北京时间 00:00**生效，历史账单和今天冻结的报价保持固定；仅调整当前操作人的直属下级，不自动向更深层级传递，相关代理需自行协调下一层。单人调价仍可为首次合同填写真实历史起始日。

真实倒挂按 `应收 − 下级应付` 记录负利润；经完整来源核对及逐级确认后，以负数扣减本人利润余额。负余额不能新申请提现，后续利润先抵扣亏损；若后来亏损已占用先前申请的提现余额，暂停登记打款，可驳回释放原冻结。缺价、金额不符或来源缺失仍阻止入账/结算。第 8 版迁移只更新带来源校验的有符号结算规则，不重算既有账单或修改历史流水。

所有角色（包括管理员）的平台显示统一使用平台名称和连接编号，包括总览、账号绑定、模型调用、授权任务、代理映射、用量、账单预览和 CSV 导出。已有内部连接名称即使保存过主账号邮箱，也不再通过这些接口返回；配置页不回显已保存的登录账号，也不再使用自定义连接名称。当前价格来自登录人的平台报价，零折扣与未定价分别显示。历史用量显示对应账单的冻结折扣，账单预览列出所选结算成员的所有有效冻结折扣，不套用管理员或今天的价格。管理员的原始对账说明不向下级返回。「打开平台」及连接配置入口仅管理员可见。

## 固定出口代理

- 「出口代理」和选择列表只显示本人添加的代理，管理员和上级也不会看到其他成员的代理池；只能绑定本人账号和本人代理。归属核实后可以在账号管理中更换自己的固定代理，系统会清空旧平台代理核实状态并自动同步支持的平台，保留原账号、平台绑定和账单历史。团队账号页仅显示其他成员账号的绑定及同步状态，不返回代理 ID、名称或出口。
- 账号的固定代理由服务器自动提供给各个平台，前端不能为某个平台单独指定其他代理。OAuth 会话、任务和最终平台绑定都记录账号代理；执行任务前再次检查启用状态和一致性。代理 URL 含认证信息时加密保存，列表只显示无认证的出口地址。
- 平台 B / 平台 C 上号时自动匹配或导入同一条代理，并使用 `manual` 和该平台代理 ID；完成后读回账号详情核对。上游隐藏认证且导入结果不明确时，任务停止并显示失败原因，需在上游核实后处理；不会只修改本地记录假报完成。禁止自动改用其他代理或直连。
- 旧账号在账号顶部绑定固定代理，平台 B / 平台 C 自动排队应用并读回验证，保留原有启停状态及全部财务历史。更换固定代理后，平台 B / 平台 C 会自动排队应用新代理；平台 A 旧账号需通过「重新授权」应用新代理。需要重试时在账号顶部「检查并同步账号代理」统一处理，不再逐个平台绑定。平台 B / 平台 C 启用前也会自动修复缺失的代理同步。
- 同步发现 平台 B / 平台 C 实际代理 ID 与映射不同时，会清除该平台的核实状态；再次启用时自动应用并读回确认，失败时不启用，也不影响向其他平台上号。上游隐藏的密码变更、平台 A 旧账号代理变更无法通过现有读取接口完整检测，仍需管理员核实；不会把未核实状态显示为已完成。
- 代理更换会先清除旧的平台代理核实状态，再按平台逐一同步；同步完成前不会把账号标记为已核实。「禁止上号」只拦截新操作，现有上游账号如需停用，请在平台管理中分别操作。

## 界面语言

默认使用英语，支持简体中文、英语、越南语和印地语（Hindi）。新访客、无效语言偏好或浏览器存储不可用时使用英语，已保存的语言选择继续保留。登录页右上角和登录后的顶部栏均可切换；语言偏好保存在当前浏览器，刷新或重新登录后继续使用，切换时保留当前表单内容。

日期和数字按所选语言显示，账单时区仍为 `Asia/Shanghai`，结算币种仍为 `USD`。账号名称、邮箱、平台代理标识和提交给服务器的业务值不随界面语言修改。

翻译目录位于 `src/locales/en.json`、`vi.json` 和 `hi.json`，以中文原文为键，动态内容使用 `{0}`、`{1}` 等占位符。添加文案时同步更新三份目录；`npm test` 检查翻译覆盖和占位符一致性，浏览器测试覆盖切换、保存偏好和手机布局。

## 代理 API 与二次开发

每位代理可在「设置与审计 → API 接入」创建独立 API 密钥，自己的后端通过 `Authorization: Bearer` 调用 CCMAX 的账号、团队、上号、用量和结算接口。默认只读，团队、账号与财务写权限可分别开启；密钥支持到期、撤销和操作审计，遵守原有团队数据范围。修改或重置密码会撤销该账号的全部密钥。

在线文档为 `/api/docs`，OpenAPI 3.1 契约为 `/api/openapi.json`，均使用当前平台主地址；无需独立域名或新增托管平台凭据。密钥只存放在代理自己的后端，浏览器通过其后端集成。详细步骤、调用示例、权限及重试规则见 [代理 API 接入](docs/AGENT_API.md)。

## 结算规则

同一账号在同一平台连接、同一天只有一条用量记录。平台账单为 `raw_usd`，本层应收为 `raw_usd × 本层折扣`，本层利润为 `本层应收 − 下级应付`。金额保存 8 位美元小数并使用数据库事务，重复同步只更新实时快照，不重复产生收益。平台接口超时、OAuth 一次性回调和 refresh token 导入不会自动重试，任务会进入「需要核对」状态，避免外部成功而本地重复记账。

确认账单前会复算完整的冻结收益链及明细汇总；提现和审核前会核对利润流水来源、原冻结和退款记录。每位用户可在「利润提现 → 核对资金账本」检查本人账本，运维可用 `npm run audit:finance` 对配置的 PostgreSQL 执行全平台只读核对。异常旧记录不会自动补造流水或改写历史。公式、修复内容、错误码及实际线下资金边界见 [资金链路核查](docs/FINANCIAL_AUDIT.md)。

管理员还可在「账单结算 / 利润提现 → 全平台资金核对」检查所有代理钱包和平台账单进度，查看历史待核实、已封账原始金额、管理员待开票应收及异常编号。网页与只读命令共用同一实现，包含预估收益链与待归属收益检查；不会自动确认收款或修改账目。平台 B 历史查询检查任务、日期、分页完整性、重复账号与金额，通过校验的完整结果由每日任务自动封账，运维接口可用于额外核查，页面无需手动采集或生成。自动采集及旧快照恢复使用第 13 版迁移，无需新增环境变量。

账单来源按实际可读数据确定：平台 A 历史接口实际返回 403 时，按连接配置使用有效日终快照预估；未采集的历史日期需上游逐账号日账单。平台 B / 平台 C / 平台 D 的完整日账单通过校验后自动封账，异常记录留档并重试。

平台 A 返回 HTTP 422 时，请先查看错误标明的失败步骤及参数名；如果提示「平台 A 的上游返回 HTTP …」，还需在 平台 A 核对其上游拒绝原因。授权回调请使用完整地址或 `code#state`。SOCKS 代理在 CCMAX 内部保存为 `socks5h://`，发送给 平台 A 时使用其公开文档的 `socks5://` 格式。上号任务失败后先核对上游账号是否已创建，再重新授权，避免重复使用一次性授权码。

部署到 Railway 后会自动执行所有缺少的迁移，第 4 版增加 平台 C，第 5 版增加固定出口代理，第 6 版增加代理 API 密钥，第 7、8 版增加资金来源及负利润约束，第 9 版增加独立运营快照和速率采样表，第 10 版允许缺失的运营金额，第 11 版增加授权码防复用，第 12 版增加每日账单库、日终快照与自动出账标记，第 13 版恢复旧快照并区分预期回退与采集异常，第 14 版增加可定价的邀请注册链接，第 15 版增加 平台 D，第 16–20 版增加隔离的 Key 供货工作空间、可复用 New API 连接、任务/渠道用量快照增量、提交幂等键、统一钱包流水和 KeyMan 定制任务模板，第 21 版记录日终快照是否已人工核实。管理员仍需在已部署实例的「平台管理」中选择 平台 D 并录入凭据和该平台独立的上游结算折扣，Git 仓库不内置真实主账号、密码或代理认证信息。

当前版本的“透传”指账号上号、平台账号同步、实时/历史用量查询、启停状态、归属和账单数据透传到 CCMAX。它还不是把 Claude API 请求反向代理到上游平台的通用 API Gateway；如果需要让下级拿 CCMAX 的 API Key 直接调用模型，需要单独增加 API 密钥、额度预扣、请求审计、流式转发和上游路由层。

详细的实现范围、安全验证及运营边界见 [上线核查](docs/VERIFICATION.md)。GitHub Actions 已配置 PostgreSQL、浏览器及 Docker 构建检查。

数据归属和展示核查、Railway 只读检查命令见 [数据归属核查](docs/DATA_ATTRIBUTION_AUDIT.md)。`npm run audit:data` 和 `npm run audit:finance` 已打包到生产镜像，可在应用容器终端直接执行；本地需先构建。

平台 B 今日为 0 时可查看「模型调用 → 近 7 天」，首页平台卡片同时展示近 7 天消费。待归属账号会显示在管理员的全平台运营统计中，但不会生成个人或代理收益。模型分类缓存延迟时，页面显示最近可用值和原始时间，并标记非实时。

## 历史单账号最高 7 天应收宣传

登录、邀请注册及成员首页可自动展示「历史单账号最高 7 天已核实应收」及对应北京时间起止日期，代理复制的推广文案也会带上该纪录。金额来自平台已有历史日账单和账号持有人的历史约定报价，不用当前邀请报价重算，不混入团队总额，不当作净利或已到账。

仅统计同一已核实归属账号连续 7 个已结束日期；按当前全部渠道绑定检查完整性，每个渠道每天均需有已核实账单和本人收益记录。缺失、快照及实时预估会使该期间不具备宣传资格，真实零账单保留。没有完整记录或读取失败时隐藏纪录，报价与注册继续可用。已有数据未区分或核实订阅档位，因此该纪录不声称是 Max 20x 的官方额度或经核实的 20x 专属纪录。

公开只读接口 `GET /api/marketing/weekly-record` 仅返回统计截止日、7 天长度、最高应收及期间，不返回账号、成员、邮箱或内部报价。查询合并并发请求并缓存 60 秒；不新增迁移，不改写账单或流水。
